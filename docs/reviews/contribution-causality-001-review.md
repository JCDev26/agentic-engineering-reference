# Contribution Causality 001 Review

## Purpose

This review records the architectural findings from testing whether contributor output can directly affect engineering validation and workflow outcome.

Previous reference slices established that:

* contributors could be selected independently from engineering intent
* capability and policy boundaries prevented unauthorized execution
* execution produced structured evidence
* engineering acceptance validation could fail even when execution succeeded

However, acceptance validation was previously performed against behavior supplied independently from contributor execution.

This experiment closes that gap.

---

## Experiment

Two contributor implementations receive the same engineering contribution.

Both contributors:

* receive the same WorkItem
* operate under the same EngineeringIntent
* participate in the same Workflow
* receive the same Contribution
* receive the same capability grant
* are subject to the same Policy
* report successful execution

They differ only in the engineering artifact they produce.

### Contributor A

Produces a duplicate-safe user creation implementation artifact.

### Contributor B

Produces a duplicate-accepting user creation implementation artifact.

The same independent acceptance validator consumes either artifact.

---

## Result

### Duplicate-Safe Contributor

```
Execution = succeeded
        ↓
Correct implementation artifact
        ↓
Acceptance validation = passed
        ↓
Evaluation = passed
        ↓
Outcome = completed
```

### Duplicate-Accepting Contributor

```
Execution = succeeded
        ↓
Incorrect implementation artifact
        ↓
Acceptance validation = failed
        ↓
Evaluation = failed
        ↓
Outcome = failed
```

The engineering contracts do not change between these paths.

---

## Architectural Finding

Contributor choice can change engineering outcome without changing engineering intent.

This demonstrates a stronger form of contributor substitutability than simply proving that multiple implementations satisfy the same execution interface.

Substitutability means contributors may participate through the same engineering contracts.

It does not mean their engineering quality or outcomes are equivalent.

Independent validation remains responsible for determining whether contributor output satisfies engineering requirements.

---

## Execution Artifacts

`ExecutionResult` now supports normalized artifact references.

The core architecture understands only:

* artifact type
* artifact reference

Scenario-specific code determines how an artifact should be interpreted.

This preserves the boundary between generic execution infrastructure and application-specific engineering behavior.

---

## Core Boundary Correction

The generic `AcceptanceValidator` contract remains in the core.

The duplicate-username validator implementation now belongs to the scenario layer because it understands:

* user creation
* duplicate usernames
* the reference application
* scenario-specific implementation artifacts

Core no longer depends on the reference application.

---

## What Is Now Defensible

The reference scenario now demonstrates that:

* the same engineering contracts can route work to different contributors
* contributors may produce different engineering results
* contributor execution success does not imply engineering success
* validation consumes contributor-produced results
* engineering outcome can differ solely because contributor output differs
* evaluation remains independent from contributor self-reporting

---

## What Is Still Not Proven

This experiment still uses in-memory implementation artifacts.

It does not yet demonstrate:

* real filesystem modification
* source diffs generated by contributors
* Git commits
* CI execution
* isolated execution environments
* human contributors
* AI contributors
* real vendor adapters
* multi-stage workflow progression

Those remain future experiments.

---

## Next Architectural Pressure

With contribution-to-outcome causality now demonstrated, the next major unresolved area becomes workflow composition.

The architecture models stages, handoffs, approvals, and multiple contributor profiles but has not yet executed a workflow containing more than one contribution.

A future experiment can now test those concepts against meaningful contributor-produced artifacts rather than simulated execution alone.

---

## Conclusion

Contributor-neutrality does not imply contributor-equivalence.

Different contributors may produce different results while operating under identical engineering contracts.

The engineering system remains responsible for independently validating those results against engineering intent.
